# 小程序成品与余料批次明细设计

## 1. 目标

补齐微信小程序的成品和余料批次明细，使手机端与电脑端使用相同数据、展示相同追溯信息，并保持相同的库存修改边界。

## 2. 一致性原则

- 小程序批次明细只读，不提供编辑、删除或手工调整入口。
- 成品数量只能通过已确认图纸入库、成品出库和流水撤销变化。
- 余料数量只能通过余料确认、余料出库和流水撤销变化。
- 电脑端 HTML 页面和小程序 JSON 接口共用 MaterialInventory、InventoryTransactionRecord 和 ScrapGenerationRecord，不建立手机专用数据或同步任务。
- 明细页每次显示时重新请求后端，不长期缓存业务数据。

## 3. 成品批次明细

### 3.1 入口

pages/inventory/list 中每个成品汇总卡片可点击，使用 product_code 跳转到新的 pages/inventory/detail 页面。卡片显示右箭头，表明可继续查看。

### 3.2 数据

复用现有 GET /api/mobile/products/{product_code}/batches 批次接口，并新增产品级流水查询能力，返回该产品关联的成品流水，而不让小程序从全局流水自行拼接。

批次展示：

- 产品型号和批次 ID。
- 当前数量和状态。
- 库位、纸材质、产品材质。
- 总成品厚度和钢板厚度。
- 创建时间和更新时间。

流水展示：

- 入库、出库或撤销类型。
- 本次数量、操作前数量和操作后数量。
- 客户/去向、操作人、备注和时间。

## 4. 余料批次明细

### 4.1 入口

pages/scraps/list 中每个余料汇总卡片可点击，使用现有 group_key 跳转到新的 pages/scraps/detail 页面。group_key 继续由材质、厚度、可用尺寸和库位构成，与小程序当前出库选择规则一致。

### 4.2 数据

新增 GET /api/mobile/scraps/batches 只读接口，接收 group_key，服务端解析并查询该组所有余料批次及相关流水。后端负责匹配库位和规格，小程序不自行筛选全局数据。

批次展示：

- 来源产品和来源图纸版本。
- 当前数量、库位和状态。
- 可用尺寸、理论尺寸和实际尺寸。
- 登记人和登记时间。

流水展示：

- 来源产品、确认入库、出库或撤销类型。
- 本次数量、操作前数量和操作后数量。
- 库位、客户/去向、操作人、备注和时间。

## 5. 小程序页面规则

- 新页面注册到 miniprogram/app.json。
- 页面使用现有 simple-header、data-list 和 state-view 组件/样式。
- 顶部显示当前规格及总数，下方分为“批次”和“流水”两组纵向卡片。
- 页面通过 onShow 重新读取数据。
- 区分加载中、空数据、连接错误和后端校验错误，并提供重试。
- 数量和时间使用现有数字样式，字段缺失时显示“-”。
- 页面不注册 confirm-sheet，不出现任何写入按钮。

## 6. 接口与错误处理

- 产品型号和余料 group_key 在 URL 中必须编码。
- 产品不存在或没有任何批次时返回空列表，页面显示空状态。
- 余料 group_key 格式错误时返回 400。
- 余料组合合法但当前没有可用批次时返回空批次和空流水。
- 接口只读，不使用 client_request_id，不创建操作日志或移动请求记录。

## 7. 测试与验收

- 先编写失败测试，再实现后端和小程序页面。
- 后端测试验证成品批次、余料批次和各自流水字段。
- 一致性测试使用同一测试数据库，比较电脑端查询所用的批次集合与手机接口结果。
- 小程序静态测试验证页面注册、汇总卡片跳转、API 调用、加载/空/错误状态和无写入控件。
- 全量运行 Python 和 Node.js 测试，确认现有入库、出库、撤销和幂等功能不回归。
- 手工验收从成品和余料汇总卡片进入明细，对照电脑端相同规格的批次、数量、库位和流水。

## 8. 不在本次范围

- 修改批次数量、库位、尺寸、备注或其他字段。
- 增加库存调整、批次删除或批次合并。
- 改变电脑端的入库、出库、撤销或余料确认流程。
- 成品出入库分析、月度汇总和备货建议。
