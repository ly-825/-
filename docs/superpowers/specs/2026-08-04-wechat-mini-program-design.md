# 厂内微信小程序总体与基础框架设计

## 1. 目标

在现有微信小程序基础上，为杭州特耐时提供厂内 Wi-Fi 环境可用的移动业务端。小程序与电脑后台共用 FastAPI 后端和同一个 SQLite 数据库，确保计划匹配、库存数量、规格排序、FIFO、流水和撤回结果一致。

第一阶段不购买云服务器，不做正式公网发布。手机必须连接工厂 Wi-Fi，后端电脑必须保持开机并运行服务。

## 2. 手机端范围

小程序只包含以下三大模块：

### 2.1 计划

- 按产品型号、名称、材质、厚度、外径、内径和齿数筛选已确认图纸。
- 选择计划产品和计划数量。
- 同时检查成品库存、匹配余料和匹配钢板。
- 显示优先使用成品、余料或钢板，以及需要采购的系统建议。

### 2.2 材料

- 钢板：规格、新增与修改、启停、入库、出库、库存、批次明细、流水、撤回。
- 余料：待入库确认、出库、库存、批次明细、流水、撤回。
- 纸材：纸圈和纸张规格、新增与修改、启停、入库、出库、库存、批次明细、流水、撤回。
- 余料不新增独立规格管理，继续由成品入库生成待确认余料，再确认实际尺寸、数量和库位。

### 2.3 成品

- 库存查询、批次明细、入库、出库、流水和撤回。
- 按型号、日期、客户、用途查看入库与出库分析。
- 显示月度汇总、销售数量和备货建议。

## 3. 暂不包含

- 图纸上传、图纸确认和图纸管理入口。
- 操作日志、智能助手和 Excel 导出。
- 扫码库存标签。
- 老板、员工等账号和角色权限。
- 离线出入库。
- 云服务器、正式域名和公网访问。

现有小程序图纸代码暂时保留，但从页面注册和导航中隐藏，不删除对应电脑后台或后端接口。

## 4. 信息架构

小程序底部使用三个入口：

1. `计划`：进入计划查料与库存匹配。
2. `材料`：先进入材料首页，再选择钢板、余料或纸材。
3. `成品`：进入成品库存与分析首页。

材料首页显示钢板、余料和纸材三个业务卡片，以及待入库余料等必要数量提示。每个模块采用“首页 → 查询/操作 → 明细/流水”的层级，不使用桌面端宽表格；列表统一使用可点击的纵向卡片。

## 5. 系统架构

### 5.1 后端

- 保留现有 FastAPI 应用、SQLAlchemy 模型和 SQLite 数据库。
- 扩展 `/api/mobile` JSON 接口，不让小程序解析电脑后台 HTML。
- 计划匹配、钢板、纸材、余料、成品和报表逻辑从现有页面处理函数中抽取或复用服务函数。
- 电脑后台与小程序接口调用同一业务服务，禁止复制一套独立计算规则。
- 保留现有运行时迁移方式，新增表或字段必须可重复执行且不破坏客户数据库。

### 5.2 小程序

- 继续使用原生微信小程序目录 `miniprogram/`。
- `miniprogram/utils/api.js` 作为统一请求入口，负责地址、超时、错误信息和请求编号。
- 公共样式统一提供卡片、筛选区、表单、状态标签、空状态、加载状态、错误状态和确认弹窗。
- 页面不直接拼接业务结果，所有显示值由接口返回的结构化字段生成。

## 6. 厂内连接设计

### 6.1 正常使用

- 后端以 `0.0.0.0:8000` 监听厂内局域网。
- 手机与后端电脑连接同一工厂 Wi-Fi。
- 小程序保存当前后端地址，例如 `http://192.168.31.68:8000`。
- 每次启动先调用 `/health` 检查连接，成功后才允许进入业务页面。

### 6.2 连接二维码

- 电脑后台新增“小程序连接”页面。
- 页面显示检测到的局域网 IPv4 地址；多网卡时允许选择或手工输入正确地址。
- 页面生成只包含版本号和后端地址的二维码，例如：

```json
{"version": 1, "base_url": "http://192.168.31.68:8000"}
```

- 小程序连接失败时显示“扫描连接二维码”和“手工设置”两个入口。
- 扫码后先校验协议、主机和端口，再调用 `/health`；只有连接成功才保存到微信本地存储。
- 二维码不包含数据库内容、密码、API 密钥或将来的用户令牌。

### 6.3 网络变化

- 手机切换到移动网络或其他 Wi-Fi 时，明确提示需要连接工厂 Wi-Fi。
- 工厂路由器或电脑 IP 改变时，重新扫描电脑后台生成的新二维码。
- 业务页面连接失败时不得继续提交库存写操作。

## 7. 写操作与数据一致性

- 所有新增、修改、启停、入库、出库和撤回操作显示二次确认。
- 确认内容必须包含当前业务对象的型号或规格，以及本次数量、单价、库位、操作人等适用字段。
- 点击提交后立即锁定按钮，直到收到明确结果。
- 每次写操作生成 `client_request_id`。
- 后端建立通用移动端请求幂等记录，按请求编号和操作类型设置唯一约束。
- 同一请求被网络重试时，后端返回首次处理结果，不重复扣减或增加库存。
- 请求结果不确定时，小程序先刷新库存与流水，再允许用户重新操作。
- 不支持离线写入和恢复网络后自动补交。
- 现有库存写锁、数据库事务、FIFO 和撤回关系继续生效。

## 8. 排序和业务规则

- 钢板继续使用厚度、宽度、长度、材质顺序。
- 纸材继续使用纸圈在前、纸张在后，同类型按型号自然排序。
- 成品继续使用产品型号自然排序。
- 计划匹配继续使用电脑后台现有成品、余料和钢板匹配条件及加工余量。
- 小程序不得自行推算库存、重量、块数、单价范围或备货建议。

## 9. 页面交互

- 搜索和筛选字段使用适合手机的单列布局。
- 大列表使用卡片和分页或分批加载，不渲染桌面宽表格。
- 支持下拉刷新；写操作成功后自动刷新相关库存和流水。
- 区分加载中、暂无数据、筛选无结果、连接失败和服务端错误。
- 数量、金额、厚度和尺寸使用等宽数字显示，避免换行导致误读。
- 危险操作（停用、撤回）使用明显的警示样式并要求填写原因；现有后端未要求原因的操作也在手机端采集备注。

### 9.1 UI/UX 设计系统

完整设计令牌与组件规则见：

- `design-system/杭州特耐时移动库存/MASTER.md`
- `design-system/杭州特耐时移动库存/pages/connection.md`
- `design-system/杭州特耐时移动库存/pages/plan.md`
- `design-system/杭州特耐时移动库存/pages/materials.md`
- `design-system/杭州特耐时移动库存/pages/products.md`

统一采用“工业化、数据优先、触控优先”的浅色界面：深石板色负责导航和层级，库存绿色只用于每屏唯一主操作及成功状态，警告和危险同时使用图标与文字。页面不使用玻璃拟态、装饰性渐变、Emoji 图标或桌面宽表格。

底部导航仅保留计划、材料和成品三个带文字的 SVG 图标入口。页面左右留白、卡片、表单和底部安全区遵循 8rpx 网格；所有触控区域至少 88×88rpx。型号、尺寸、数量和金额使用等宽数字并允许合理换行，确保流水、备注和尺寸不再被压成窄列。

写操作统一使用单列表单、常驻字段标签、就近错误提示、底部固定提交按钮和字段核对弹层。计划匹配使用结论卡与三类库存卡；材料和成品流水统一使用纵向事件卡；出入库分析仅使用折线图和水平条形图，并始终附带可读数值。

## 10. 实施阶段

### 阶段 1：基础框架

- 三个底部入口和材料首页。
- 后端连接检测、电脑连接二维码、扫码配置和手工配置。
- 通用请求、错误、加载、空状态、确认弹窗和防重复点击。
- 后端移动请求幂等基础设施。
- 保留现有业务数据，不迁移或重写库存记录。

### 阶段 2：计划查料

- 计划筛选、图纸选择、计划数量、三类库存匹配和建议。

### 阶段 3：钢板材料

- 规格、入库、出库、库存、明细、流水和撤回。

### 阶段 4：纸材材料

- 纸圈与纸张规格、入库、出库、库存、明细、流水和撤回。

### 阶段 5：余料材料

- 整合并完善现有待确认、库存、出库和流水页面，增加批次明细一致性。

### 阶段 6：成品

- 整合并完善现有库存、入库、出库和流水页面，增加明细与出入库分析。

### 阶段 7：整体验收

- 手机和电脑数据一致性、网络中断、重复请求、常见手机尺寸和厂内 Wi-Fi 真机验收。

每个阶段独立编写实施计划、测试、提交和推送，通过验收后再进入下一阶段。

## 11. 第一阶段验收标准

- 小程序启动后只显示计划、材料和成品三个底部入口。
- 材料首页可进入钢板、余料和纸材占位首页，尚未完成的操作明确标识为后续阶段，不出现不可解释的空白页。
- 后端在线时，小程序自动完成健康检查并进入业务导航。
- 后端地址缺失或不可访问时，小程序进入连接引导页，不显示可执行库存操作。
- 扫描电脑连接二维码后，可以校验并保存后端地址；重启小程序后继续使用该地址。
- 地址失效后可以重新扫码或手工修改。
- 通用确认弹窗能够完整展示即将提交的字段。
- 同一 `client_request_id` 的示例写请求重复发送时，后端只处理一次。
- 现有电脑后台和现有数据库功能不受影响。
- 后端自动化测试全部通过，小程序在微信开发者工具和至少一台连接工厂 Wi-Fi 的真机上通过连接测试。

## 12. 后续权限兼容

上述七个功能阶段全部完成后，再启动独立的权限项目，引入用户身份和角色：老板可查看与修改完整资料，员工按授权执行出入库。当前接口路径、请求编号、操作确认和审计字段必须预留用户身份传递位置，但本设计的七个阶段均不实现登录、角色判断或权限拦截。
